# Notes, Blog and Reports. What was built, and what has not been proved.

2 September 2026.

## What is live

Four tabs on the command centre: Today, Notes, Blog, Reports. Hash routed, so
`/#notes`, `/#blog` and `/#reports` are linkable and bookmarkable, and The One
Thing links straight to the Blog tab.

The tab bar and the three new tabs are ONE file, `netlify/functions/tabs.html`,
injected by `site.js` at request time exactly like the chat. The twice-daily
refresh task rewrites `command-centre.html`, which is now the Today tab and
nothing else. It cannot break the other three, and it does not have to rebuild
them. Response header `x-nuvo-tabs` says `on` when the file made it into the
deploy.

Three new endpoints, all behind the same session or task token:

| endpoint | store | who writes what |
|---|---|---|
| `/api/notes` | `nuvo-notes` | Ben adds, edits, opens and closes. The task marks a note surfaced and writes the weekly line. Nothing deletes. |
| `/api/blog` | `nuvo-blog` | The task creates and publishes. Ben saves, approves and rejects. Approve and reject are refused for a task token. |
| `/api/reports` | `nuvo-reports` | Ben requests, opens, resumes and drops. The task defines and runs. Define needs all four of name, owner, purpose and decision. |

## The three rules that shaped the code

**A note is never deleted.** There is no DELETE method on `/api/notes` and no
expiry sweep. Closing takes it off the pad and keeps the record. The value of
the pad is the fourth time in six weeks he writes a version of the same note,
and a pad that forgets cannot show him that. If the store ever outgrows one
list call, page it. Do not start deleting.

**Approving does not publish.** WordPress is reached over Zapier under Ellie's
account. A Netlify function has no business holding those credentials, so
approve marks the record and the blog task creates the WordPress draft on its
next run and posts the URL back. Consequence: an approval on Saturday reaches
WordPress on Friday. If that latency ever matters, the fix is a second trigger,
not credentials in a function.

**The thirty day pause is applied on read.** Not by a nightly job. A rule that
needs a job to run is a rule that silently stops holding. Opening the report
resets the clock; opening the tab does not, or the rule would never fire.

## Voice lessons

`claude/voice-lessons.md` is new. The app diffs Ben's edit against the draft the
task originally wrote, sentence by sentence, and stores the changed pairs. The
blog task turns those into lines in that file and reads it before writing the
next post. The diff is computed in the function, not by the task, so a lesson
survives the post being edited again later.

This is the only part of the build that gets better on its own. It also does
nothing at all until Ben edits a draft.

## What was verified, and how

Against the live site, not locally.

- Notes: create, close, reopen, refuse to empty, insight write and clear, no
  DELETE method (405), page cannot write the insight or mark surfaced (403).
- Blog: task creates, Ben edits, the diff produced a real lesson ("We are
  pleased to announce a change. It is a game changer for our customers." became
  "We stopped quoting over the phone. A phone number cannot tell you what is
  behind your siding."), approve moves it to the task's publish queue, reject
  without a reason is refused, task cannot approve or reject.
- Reports: five requested, the sixth returned `needsDrop` with the five named,
  naming one to drop let the sixth through.
- The thirty day pause: eight unit cases including the four that must NOT pause.
- The whole page in a real DOM with the API stubbed, before deploying.

All verification records were then cleared. The two notes it created are closed,
not deleted, because that is the rule.

## What has NOT been proved

- No scheduled run has touched any of this yet. First real test is the 6:30am
  page build on 3 September, then the 7am email, then the Friday blog task.
- The weekly notes insight has never been written by a task.
- No report has ever been built, so `define` and `run` are untested from the
  task side.
- The blog task's step 0 has never run. On 4 September all three of its queues
  will be empty, which is the correct first-run outcome and proves nothing.

## The tension worth naming

Ben's standing rule is one email a day. The blog task still sends its own on
Friday, because it creates the draft at 9am and The One Thing has already gone
at 7am, so there would be no same-day notice otherwise. From the following
Monday The One Thing carries it as one line with a link, which is what he asked
for. The blog email is marked in its own prompt as on notice.
